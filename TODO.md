## Правила

- Ставить галочку (`- [x]`) можно только когда выполнен **критерий «Готово»** задачи.
- Порядок важен: Фазы 0 → 1 → 2 → 3 → 4 — нельзя перепрыгивать (они чинят потерю данных).
- После каждой фазы — отдельный коммит.
- `docs/PLAN.md` меняем только когда правка касается самого плана; TODO.md — просто трекер.
- Метки задач: **[FE]** — делается в этом репозитории; **[BE]** — в бэкенд-репо
  `LedgerCraftDocker03` (Laravel); **[FE+BE]** — одной стороной задачу не закрыть.
- В фазах, где серверной части нет вообще (1, 2, 4, 6, 8), все задачи — `[FE]` и метка не ставится;
  разбивка `FE/BE` в сводке показывается только там, где есть `[BE]`/`[FE+BE]`.
- Задача с `[BE]`/`[FE+BE]` считается выполненной только после коммита в бэкенд-репо **и**
  проверки на сервере (либо теста в `LedgerCraftDocker03`); критерий «Готово» описывает обе стороны.
- В бэкенд-репо не трогаем незакоммиченные `docker-compose.yaml`, `sync/`, `_docker/sync/` —
  до отдельной договорённости (см. 3.11).
- **Среды (с 12.09.2026):** **dev-VPS** (`dev.medovf2h.beget.tech`) — песочница, здесь пробуем новые
  фичи и не боимся снести БД; **prod-VPS** — боевой контур с реальными данными, туда попадает
  **только проверенное на dev**. Порядок: dev → проверка по чек-листу (11.5) → prod (11.12).
- **Отчёты «Сообщить об ошибке» (Фаза 14, решение D7):** выгружаем `npm run feedback:pull`; у каждого
  отчёта в `feedback/DECISIONS.md` должен быть вердикт — **баг** → задача в этом файле с приоритетом и

## Решения

Приняты 11.09.2026 по итогам сверки с кодом бэкенда (детали — `docs/API-INTEGRATION.md` §4–6).

- **D1. Синк — только Laravel.** `/api/sync` + `/api/sync-updates` (`SyncController`) остаются
  единственным транспортом. Go-сайдкар `sync/` выносится из `master` в песочницу; из него в
  Laravel переносим **SAVEPOINT-изоляцию операций** (одна плохая операция не валит весь батч) и
  вырезание `server_id`/`*_server_id` из payload → задачи **3.11**, **3.5**.
- **D2. Материалы = позиции заказа.** Товар со склада → `order_product` (списание/возврат остатка),
  «купил по пути» → ручная позиция. В обе позиции добавляется **`buy_price`** (себестоимость) →
  считается маржа/наценка → задачи **3.4**, **9.5**, **9.6**. Клиентский справочник `materials`
  (миграция 018) удаляется; **новая серверная таблица `order_material` не нужна**.
- **D3. Web-версия бэкенда — продукт (принято 12.09.2026).** `resources/js` + blade'ы +
  `save_order`/`update_order` + `Auth::routes()` не легаси: её сохраняем и не удаляем, поэтому
  объём 7.6 ограничен чисткой мёртвого/дублирующего (недостижимый `auth:api`, дубль
  `switch_paid_status`, не зароутенный `MaterialController::create`). Публичный отчёт
  `/order-report` остаётся и связан с share-ссылкой (задача 9.4).
- **D4. Специализация = рабочий профиль, а не «тип аккаунта» (принято 12.09.2026).**
  «Специализация» уже первоклассная сущность: на сервере `User hasMany Specialization`
  (`specializations.user_id`, миграция `2024_03_08_085324_add_user_id_to_specializations_table`),
  а на клиенте к `specialization_id` привязано всё остальное — `categories` → `services`,
  `product_categories` → `products`, `equipment_models`, `clients`, `orders`; синк уже фильтрует
  выдачу по цепочке владельцев (`specializations.user_id` → `orders.user_id` → дети, задача 3.10).
  Значит **мульти-специализация** («веломастер + аквариумист») **не требует переделки схемы** —
  нужны только продуктовая оболочка и UX. Активная специализация в UI =
  `useSpecializationsStore.selectedId`; переключение — смена рабочего контекста
  (заказы/клиенты/каталог/склад), а не выход из аккаунта. Переключатель переезжает из «Другие»
  в шапку (`MainLayout.vue`) → задача **10.8**.
- **D5. Пресеты специализаций + адаптация UI (принято 12.09.2026, реализовано в Фазе 10).**
  «Пресет» = стартовый каталог (категории работ → услуги с ценами, категории товаров, модели
  техники) + метаданные UI (словарь терминов, акцентный цвет, видимость вкладок). Правила:
  - **клонируем, а не ссылаемся:** применение пресета материализует обычные записи мастерской с
    пометкой происхождения (`template_key`); дальше это данные пользователя, он их правит;
  - **идемпотентность:** повторное применение не дублирует каталог (уникальность
    `(specialization_id, template_key)`) → задача **10.4**;
  - **источник пресетов — сервер**, клиент держит read-only кэш в `meta` + фолбэк на клиентский
    JSON (офлайн-первый вход) → задача **10.7**;
  - **архивируем, а не удаляем:** у серверных `categories`/`product_categories` есть FK на
    `specializations` с `onDelete('cascade')`, поэтому «убрать специализацию» = флаг `archived`
    (иначе каскад снесёт каталог) → задачи **10.6**, **10.8**;
  - **раскраска — только акцентом** (runtime `setCssVar` в Quasar 2), без пересборки SCSS и полного
    ре-скина; **схему заказа под нишу не ветвим** (универсальная модель + максимум 1–2 опциональных
    поля вроде `equipment_identifier` — VIN / серийник рамы / адрес объекта) → задачи **10.2**, **10.9**.

  **Первые четыре специализации (v1):** ремонт велосипедов (`bike`), мастер по аквариумам
  (`aquarium`), установка и обслуживание кондиционеров (`hvac`), автосервис (`auto`). Дальше
  перечень расширяется — пресеты это контент, а не код.

  **Не делаем (осознанно):** schema-per-ниша, отдельные формы заказа под каждую специализацию,
  CRDT/version-vectors — выигрыш в «универсальности» близок к нулю, а офлайн-модель и синк ломаются.
- **D6. Обновление Android-приложения — свой канал, без Play и без Cordova (принято 13.09.2026).**
  Приложение раздаётся APK со своего сервера (файл кладёт `php artisan app:publish-apk`), клиент
  сам проверяет версию и по кнопке вызывает системный установщик (`PackageInstaller`). Причины:
  Play-канал пока не планируется, а политика Play запрещает самообновление APK (JS внутри WebView —
  разрешает, но это отдельный этап); Cordova не используем вовсе (в проекте Capacitor, Cordova-слоя
  в `@capacitor/core` 7 нет) — поэтому HCP-заготовки (`/api/hcp/chcp.json`, папка `hcp/` в бэкенде,
  `cordova-plugin-hot-code-push`) остаются легаси и не оживляются. «Критерий новее» — `versionCode`
  (целое), «тихой» установки без диалога быть не может (только Play или Device Owner) — это
  ограничение Android, а не реализации. OTA веб-слоя (`@capawesome/capacitor-live-update`, MIT,
  self-hosted) — задача будущего этапа, точка расширения уже готова (`updateService`).
  → задачи **13.1–13.15**
- **D7. Отчёты об ошибках — отдельный контур, не синк (принято 13.09.2026).** Кнопка «Сообщить об
  ошибке» должна работать офлайн и складывать отчёты туда, где их прочитает разработчик **и
  ИИ-агент**, которому доступны файлы репозитория. Поэтому: (1) отчёт — **не** таблица синка (новый
  `type` в `$tables`/`TABLE_ORDER`, «полный сброс» и восстановление из бэкапа тащили бы его за собой,
  а второе устройство владельца видело бы чужие отчёты); (2) локально — своя очередь
  `feedback_reports` по образцу `operations` (3.3); (3) на сервере — таблица `feedback_reports` +
  `POST /api/feedback` (идемпотентность по `uuid_id`, как в 3.5) + выгрузка `GET /api/feedback` под
  отдельным pull-токеном; (4) последнее звено — инбокс в репо (`feedback/INBOX.md`,
  `npm run feedback:pull`), чтобы отчёт читался без БД и без SSH. Отвергнуто: GitHub Issues прямо из
  приложения (токен в APK), Telegram-бот/e-mail (агент не читает переписку), внешняя крашлитика
  (приватность мастерской, офлайн-первый сценарий). В отчёт **не попадают** данные заказов/клиентов,
  отправка — только по действию пользователя. Контракт и цепочка — `docs/FEEDBACK.md`
  → задачи **14.1–14.10**
