# Обратная связь: «Сообщить об ошибке» и приём отчётов

> План принят 13.09.2026, **реализовано** (задачи 14.1–14.7: клиент + сервер; 14.8–14.10 — сверху).
> Задачи — `TODO.md` §«Фаза 14», решение — **D7**. Схему синка документ не меняет: отчёты —
> **отдельный контур**, а не бизнес-таблицы мастерской.

## 1. Задача

Мастер работает на телефоне, консоли разработчика там нет (частично закрыто «режимом разработчика»,
задача 12.5 — но он требует, чтобы мастер догадался включить тумблер). Нужно:

- кнопка **«Сообщить об ошибке»**, которая работает **офлайн** (как и всё приложение);
- отчёт складывается туда, где его прочитает **разработчик** и **ИИ-агент** (Cline);
- в отчёт не попадают данные мастерской (заказы, клиенты, суммы).

Ключевое ограничение постановки — «хранить так, чтобы агент смог прочитать». Агент читает **файлы в
рабочем каталоге репозитория**, поэтому последнее звено цепочки — не БД, не мессенджер и не почта, а
**инбокс-файл в репо**: `feedback/INBOX.md` (+ сырые файлы `feedback/inbox/*.md`).

## 2. Цепочка целиком

```
телефон мастера                       сервер (Laravel)                 репозиторий FE            агент/разработчик
─────────────────                     ────────────────                 ─────────────            ─────────────────
ошибка / жалоба мастера
   │
   ├─ errorLog — постоянный буфер ошибок (window.onerror, unhandledrejection,
   │            app.config.errorHandler, logger.error/warn) — живёт без dev-режима
   ▼
диалог «Сообщить об ошибке» (тип, текст, «приложить диагностику»)
   │  feedbackService.submit(kind, message, attachDiagnostics)
   ▼
локальная очередь feedback_reports  ──POST /api/feedback──►  feedback_reports
   (статус pending; нет сети —               (auth:sanctum,      (uuid_id unique)
    отчёт никуда не теряется)                 идемпотентность)
   │                                                 │
   └─ сеть появилась → flush() ──────────────────────┘
                                                     ▼
                                        GET /api/feedback (X-Feedback-Token)
                                        или `php artisan feedback:export`
                                                     │
                                                     ▼
                                   npm run feedback:pull → feedback/INBOX.md
                                                           feedback/inbox/*.md
                                                     │
                                                     ▼
                                   агент читает INBOX.md → баг-задача в TODO.md
                                   (правило 14.9: ни одного отчёта «в воздухе»)
```

## 3. Контракт отчёта (`POST /api/feedback`)

```json
{
  "uuid_id": "b7f1c0de-…",
  "kind": "bug",
  "message": "при добавлении работы кнопка «сохранить» ничего не делает",
  "contact": "",
  "screen": "/orders/42",
  "app_version": "1.1 (2)",
  "platform": "android",
  "platform_version": "Android 13",
  "device": null,
  "api_url": "https://dev.medovf2h.beget.tech/api",
  "schema_version": 30,
  "schema_stored": 30,
  "account": "master@example.com",
  "profile": "Велосервис",
  "sync": {
    "online": false,
    "pendingCount": 3,
    "failedCount": 0,
    "consecutiveFailures": 2,
    "lastError": "Network Error"
  },
  "errors": [{ "time": "2026-09-13T20:10:59.000Z", "level": "error", "message": "…" }],
  "logs": [{ "time": "2026-09-13T20:10:58.000Z", "level": "log", "message": "…" }],
  "client_created_at": "2026-09-13T20:11:03.000Z"
}
```

| Поле                              | Смысл                                              | Источник                                       |
| --------------------------------- | -------------------------------------------------- | ---------------------------------------------- |
| `uuid_id`                         | id отчёта на устройстве → идемпотентность повторов | `crypto.randomUUID()` (как в синке 3.5)        |
| `kind`                            | `bug` \| `suggestion` \| `question` \| `crash`     | выбор мастера в диалоге                        |
| `message`                         | текст мастера, 3…4000 символов                     | ввод                                           |
| `contact`                         | как ответить мастеру (необязательно)               | ввод                                           |
| `screen`                          | экран, где было (маршрут)                          | `router.currentRoute.value.fullPath`           |
| `app_version`                     | `versionName (versionCode)` из сборки              | задача 13.5 (`@capacitor/app`)                 |
| `platform`, `platform_version`    | `android` \| `web`, версия ОС                      | `src/utils/platform.js`                        |
| `device`                          | модель устройства (пока `null`)                    | появится с `@capacitor/device`                 |
| `api_url`                         | контур (dev/prod)                                  | `src/config.js`                                |
| `schema_version`, `schema_stored` | эталон схемы и то, что в БД                        | `SCHEMA_VERSION`, `adapter.getSchemaVersion()` |
| `account`, `profile`              | аккаунт и активный профиль                         | `useAuthStore`, `useSpecializationsStore` (D4) |
| `sync`                            | состояние синка на момент отчёта                   | `SyncService.getStatus()`                      |
| `errors`                          | хвост постоянного буфера ошибок (≤ 50)             | `src/utils/errorLog.js`                        |
| `logs`                            | кольцевой буфер `logger` (≤ 100, по согласию)      | `getLogBuffer()` (12.5)                        |
| `client_created_at`               | время на устройстве                                | `new Date().toISOString()`                     |

Правила:

- Диагностика собирается **тем же представлением, что «снимок для поддержки»** (`src/utils/devInfo.js`,
  `buildDiagnosticSnapshot`, задача 12.5): не заводим второй формат для того же смысла.
- Два уровня логов: `errors` (всегда) и `logs` (только если включена галочка «приложить диагностику»).
- Обрезка **на клиенте и на сервере**: ≤ 50 error-записей, ≤ 100 log-записей, сообщение лога ≤ 500
  символов, текст мастера ≤ 4000. Тело запроса — ≤ 256 КБ.

## 4. Приватность: чего в отчёте быть не должно

- **Никаких данных мастерской:** заказов, клиентов, телефонов, сумм, VIN. Сборщик payload берёт только
  поля из §3 — это закрыто тестом (задача 14.3).
- Логи — сообщения **нашего кода** (`logger.*`); содержимое заказов там не печатается. Если где-то
  печатается — это дефект логгера, а не разрешение класть это в отчёт.
- `contact`/`account` — по желанию мастера; без них отчёт анонимный, кроме `user_id` на сервере
  (нужен, чтобы связать отчёт со свежей версией приложения и ответить).
- Отправка **только по действию пользователя**: тихой телеметрии и автоотправки без согласия нет.
  Даже авто-отчёт о сбое (14.8) лишь **предлагает** отправить.
- Сырые отчёты и дайджест (`feedback/inbox/`, `feedback/INBOX.md`) — в `.gitignore`: логи и аккаунт
  не уезжают в публичный репозиторий. В git живут только `feedback/README.md` и
  `feedback/DECISIONS.md` (разборы, без персональных данных).

## 5. Почему отдельный контур, а не синк (решение D7)

| Вариант                                | Почему не он                                                                                                                                                                                                                                |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Через `/api/sync` (как бизнес-таблицу) | нужен новый `type` в `$tables` и `TABLE_ORDER` на обеих сторонах; отчёты уезжают всем устройствам владельца и приезжают в `sync-updates`; «полный сброс»/восстановление из бэкапа тащит за собой чужие отчёты. Отчёт — не данные мастерской |
| GitHub Issues напрямую из приложения   | нужен токен в APK (утечка), репозиторий может быть приватным, офлайн не работает                                                                                                                                                            |
| Telegram-бот «в личку»                 | делается быстро, но у агента нет доступа к переписке — требование «чтобы агент читал» не выполняется                                                                                                                                        |
| E-mail                                 | то же: агент не читает почту; на устройстве нужен почтовый клиент                                                                                                                                                                           |

Итог: **свой эндпоинт + таблица + выгрузка в файлы репозитория**. Бонус: разборы и история живут
рядом с кодом, выгрузка работает и вручную (файл/SSH), и по HTTPS.

## 6. Локальная часть (клиент)

| Что                     | Файл                                                                                                                      | Роль                                                                                                                                                                                      |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Постоянный буфер ошибок | `src/utils/errorLog.js`                                                                                                   | кольцо на 100 `warn`/`error`, переживает перезапуск, пишется **всегда** (в отличие от `utils/logger.js`, который копит буфер только в dev или при включённом «режиме разработчика», 12.5) |
| Глобальные перехватчики | `src/boot/errorLog.js` (новый boot-файл)                                                                                  | `window.onerror`, `window.onunhandledrejection`, `app.config.errorHandler`                                                                                                                |
| Очередь отчётов         | миграция `030_create_feedback_reports_table.js` + `src/repositories/feedbackRepo.js` + `src/database/queries/feedback.js` | `uuid_id`, `kind`, `message`, `payload`, `status` (`pending`/`sending`/`sent`/`failed`), `attempts`, `last_error`, `created_at` — по образцу `operations`/`operationsRepo` (3.3)          |
| Сборка отчёта           | `src/utils/feedbackView.js`                                                                                               | чистые функции: `buildFeedbackReport(...)`, `canSubmitFeedback(text)`, `feedbackStatusView(...)`, обрезка логов и текста                                                                  |
| Отправка                | `src/services/feedbackService.js`                                                                                         | `submit()` (пишет локально → пробует уйти → офлайн остаётся `pending`), `flush()` (досылает; зовётся рядом с синком — `App.vue`/`boot/db.js`), `pendingCount()` для UI                    |
| UI                      | `src/pages/dialogs/FeedbackDialogPage.vue` (по конвенции диалогов) + кнопка во вкладке «поддержка» (`src/components/settings/SettingsDialog.vue`) | тип, текст, «приложить диагностику», «копировать текст в буфер» (аварийный путь), состояние «сохранён и будет отправлен»                                                                  |

Поведение при ошибках отправки: сеть/таймаут → `pending` (повтор при следующем `flush()`);
`401` → `failed` + сообщение «нужно войти»; `422` → `failed` (отчёт сохранён локально, текст можно
скопировать); `429` → `pending`. Отчёты отправляются по одному: битый/отклонённый не блокирует
остальные, батч не нужен (отчётов мало).

## 7. Серверная часть (`LedgerCraftDocker03`)

Таблица `feedback_reports`: `uuid_id` (unique), `user_id` (nullable), `kind`, `message`, `contact`,
`screen`, `app_version`, `platform`, `platform_version`, `device`, `api_url`, `schema_version`,
`schema_stored`, `account_email`, `profile_name`, `payload`/`sync`/`errors`/`logs` (jsonb),
`client_created_at` (время на устройстве), `status` (`new`/`read`/`accepted`/`rejected`),
`resolution_note`, `ip`, `user_agent`, `created_at`/`updated_at` (время приёма сервером).

| Ручка                                           | Доступ                                                                            | Поведение                                                                                                                                                          |
| ----------------------------------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /api/feedback`                            | `auth:sanctum` + `throttle:10,60`                                                 | валидация + обрезка; идемпотентность по `uuid_id` (повтор отдаёт тот же `server_id`, дубля нет — приём из 3.5); ответ `201 { ok, server_id, uuid_id }`             |
| `GET /api/feedback?since=&limit=&status=`       | **только** `X-Feedback-Token` (env `FEEDBACK_PULL_TOKEN`), **вне** `auth:sanctum` | выгрузка для разработки/агента; пользовательский токен мастерской сам по себе чужих отчётов не отдаёт (`403`), пустой токен в конфиге = выгрузка выключена (`503`) |
| `PATCH /api/feedback/{uuid_id}`                 | pull-токен                                                                        | статус разбора: `new`/`read`/`accepted`/`rejected` + заметка — чтобы один отчёт не заводили дважды                                                                 |
| `php artisan feedback:export [--since=] [--md]` | SSH/CLI                                                                           | файл-дайджест на сервере (путь, когда HTTPS-выгрузки нет)                                                                                                          |

Канонический контракт бэкенда — `LedgerCraftDocker03/docs/API.md` §5 и `docs/DB.md`
(`feedback_reports`), клиентское зеркало — `docs/API-INTEGRATION.md` §2.6.

## 8. Инбокс в репозитории — «то, что читает агент»

```
feedback/
├── README.md      # как работает цикл (в git)
├── INBOX.md       # дайджест: свежие сверху (в .gitignore)
├── inbox/         # по файлу на отчёт: <дата>-<короткий-uuid>.md (в .gitignore)
└── DECISIONS.md   # журнал разбора: отчёт → задача / «не баг» + объяснение (в git)
```

- `npm run feedback:pull` → `scripts/pull-feedback.mjs`: тянет `GET /api/feedback` с pull-токеном и
  раскладывает файлы. Адрес и токен — из `.env.local` (`VITE_API_URL`, `FEEDBACK_PULL_TOKEN`), в git
  не попадают. Скрипт умеет и `--file=<путь>` — положить готовый отчёт, присланный вручную.
- Агенту доступны те же файлы локально (даже игнорируемые git), поэтому цикл «отчёт → чтение →
  задача» не требует доступа к БД, SSH или сторонним сервисам.
- Аварийный путь без сервера: диалог даёт «копировать текст в буфер» (тот же
  `buildDiagnosticSnapshot`), мастер пересылает текст любым каналом, файл кладут в `feedback/inbox/`
  руками — задачи 14.5 и 14.7.

## 9. Цикл разбора (правило, как 11.5)

1. `npm run feedback:pull` (или руками в `feedback/inbox/`).
2. Каждый отчёт → запись в `feedback/DECISIONS.md`: **баг** → задача в `TODO.md` (ближайшая
   подходящая фаза, с приоритетом и критерием «Готово»); **не баг / предложение** → запись с
   объяснением, почему.
3. Регресс закрывается тестом, как обычно; в коммите — ссылка на файл отчёта.
4. Ни один отчёт не остаётся «в воздухе» — критерий приёмки 14.10.

## 10. Что не делаем (осознанно)

- Автотелеметрию и крашлитику без действия пользователя.
- Внешние SaaS-приёмники (Sentry и т. п.): приватность мастерской и офлайн-первый сценарий важнее;
  контракт отчёта не мешает позже добавить приёмник.
- Вложения от мастера (скриншоты): на Android это отдельные разрешения и трафик; сначала текст +
  диагностика.
- Автосоздание задач парсером: «баг или нет» решает человек/агент, а не регулярка.

## 11. Критерий «фаза закрыта»

- **Офлайн:** сеть выключена → отчёт отправлен → он `pending` и виден в диалоге; сеть появилась →
  уезжает без действий мастера.
- **Идемпотентность:** повтор запроса/повторная отправка не создаёт дубля в `feedback_reports`.
- **Приватность:** в payload нет полей заказов/клиентов (тест 14.3); логи и текст обрезаны по лимитам.
- **Чтение агентом:** `npm run feedback:pull` кладёт отчёт в `feedback/INBOX.md`; отчёт читается без
  SSH и без БД; разбор зафиксирован в `feedback/DECISIONS.md`.
- **Прогоны:** FE `npm test` (миграции/очередь/payload/буфер) и `npm run lint` — 0; BE
  `php artisan test` (`FeedbackTest`); живой отчёт с телефона на dev-VPS.
