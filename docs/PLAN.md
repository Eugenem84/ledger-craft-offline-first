# План развития Ledger Craft (дорожная карта)

> Этот план составлен по результатам ревью кода (см. `docs/ARCHITECTURE.md`,
> `docs/FRONTEND.md`, `docs/API-INTEGRATION.md`, `docs/DATA-MODEL.md`). Он фиксирует **что**, **зачем**
> и **в каком порядке** делать, чтобы проект перестал «терять данные» и начал честно работать
> как offline-first система.
>
> Приоритеты: **P0** — данные теряются/невозможно работать в проде, **P1** — больно и дорого
> поддерживать, **P2** — хочется, но не блокирует.
>
> Оценки объёма — «человеко-дни» для соло-разработчика, который уже знаком с кодом.

## 0. Итоговая дорожная карта (одним взглядом)

| Этап | Что даёт | Объём |
|---|---|---|
| **Фаза 0** — гигиена репозитория | чистая база, lint проходит, меньше шума | ~1 день |
| **Фаза 1** — персистентная локальная БД | данные переживают перезапуск приложения | ~1–2 дня |
| **Фаза 2** — схема и миграции | одна истина в схеме, единые деньги, честные транзакции | ~2–3 дня |
| **Фаза 3** — переписать синхронизацию | связные таблицы синкаются, без костыля «двойной прогон» | ~3–5 дней |
| **Фаза 4** — нативный SQLite (Capacitor) | Android: настоящий SQLite на диске | ~1–2 дня |
| **Фаза 5** — тесты | регрессии ловятся автоматически (особенно по синку) | ~2–3 дня |
| **Фаза 6** — UX офлайна | приложение не блокируется на синке, есть индикатор сети | ~1–2 дня |
| **Фаза 7** — конфигурация и безопасность | env, токены, осмысленный вход | ~1–2 дня |
| **Фаза 8** — рефакторинг UI | OrderDetailsPage 1042 строки → компоненты | ~1–2 дня |
| **Фаза 9** — продукт (аналитика и «сироты») | работающая аналитика, чистая модель данных | ~3–5 дней |

> **Почему такой порядок:** сначала чиним то, что убивает данные (Фаза 1–4), только потом
> наводим красоту и добавляем фичи. Странно улучшать UI, пока каждое закрытие приложения
> стирает всю учётку.

**Зачем:** текущий адаптер `sqljs-web-adapter.js` создаёт БД в памяти и **ни разу не сохраняет

Плюс WASM грузится с CDN — без интернета приложение не стартует. Это делает весь
«offline-first» фикцией.

### Задачи

## Фаза 3 — Переписать синхронизацию (P0, самый большой кусок)

**Зачем:** сейчас `sync()` дважды вызывает `_syncLocalToServer()` — это костыль под
двухфазную отправку «родитель → ребёнок», но он не гарантирует порядок. Операции детей
откладываются просто «в очередь», если у родителя ещё нет `server_id`. А `order_product`
и `order_material` вообще не участвуют в синке — их INSERT улетают с локальным UUID в
`order_id`, а обратно не приходят.

### Задачи

| ID | Приоритет | Задача | Действия | Критерий «Готово» |
|---|---|---|---|---|
| 3.1 | P0 | Убрать двойной вызов `_syncLocalToServer()` | Удалить вторую строку в `sync()` | в `sync()` вызов `_syncLocalToServer()` — один |
| 3.2 | P0 | Топологическая сортировка операций | Перед отправкой строить граф зависимостей из `fkTransformationMap` и `*_server_id`-полей; отправлять родителей раньше детей; если зависимость не готова — откладывать конкретную операцию, а не весь батч | ребёнок никогда не отправляется раньше родителя |
| 3.3 | P0 | Статусы операций (не удалять сразу) | В `operations` добавить `status` (`pending`/`sending`/`synced`) и `updated_at`; `dequeue` берёт только `pending`; `markSynced` удаляет только после атомарного успеха | операция не «теряется» при сбое между отправкой и ответом |
| 3.4 | P0 | Подключить связные таблицы | Добавить в `repos` и `fkTransformationMap`: `order_product`, `order_material`, `materials`. Реализовать `applyServerRecord` (перевод `order_id`/`product_id`/`service_id`/`material_id` из server_id в локальные UUID) | тест: созданный офлайн ордер с товарами и материалами полностью уезжает и приезжает на второй устройство |
| 3.5 | P1 | Идемпотентность | Сервер/клиент должны выдерживать повторную отправку одной операции без дублей (по `local_id`/UUID и `server_id`) | повторный синк не создаёт дубликатов |
| 3.6 | P1 | Курсор `last_synced_at` на таблицу | Сейчас одна метка на все таблицы — перейти на `key = 'last_synced_at:<table>'` или колонку `table` в `meta` | после сбоя в одной таблице другие продолжают с прошлого курсора |
| 3.7 | P1 | Обработка ошибок сети | Эскалация ретраев (backoff), при сетевой ошибке операция остаётся в очереди, UI показывает «нет сети» | нет бесконечного цикла отправки одного батча |
| 3.8 | P1 | Версионирование/конфликты | `updated_at`-сравнение оставить как начальную версию, но задокументировать известные конфликты (last-write-wins) | поведение при конфликте описано и покрыто тестом |

## Фаза 4 — Нативный SQLite через Capacitor для Android (P1)

**Зачем:** сейчас локальная БД — sql.js (WASM в памяти). На Android правильнее
использовать настоящий файл SQLite через `@capacitor-community/sqlite` — он быстрее,
надёжнее и работает по-настоящему персистентно. В коде уже есть заготовка
`src/database/adapters/sqlite-capacitor-adapter.js`, но она не подключена, а зависимости
в `package.json` нет.

### Задачи

| ID | Приоритет | Задача | Действия | Критерий «Готово» |
|---|---|---|---|---|
| 4.1 | P1 | Добавить зависимости | `npm i @capacitor/core @capacitor/community/sqlite jeep-sqlite @capacitor/cli` | сборка/запуск не падают |
| 4.2 | P1 | Довести адаптер | В `sqlite-capacitor-adapter.js`: корректно открыть БД (`open`), `execute` для DDL (`statements` массив), `executeSet` для параметризованных insert/update, `query` с `{statement, values}`, `transaction` (begin/commit/rollback) | тест: создание таблицы миграцией + CRUD на Android |
| 4.3 | P1 | Переключить boot на платформу | В `src/boot/db.js` выбирать адаптер по `Capacitor.isNativePlatform()`: Android → нативный SQLite, браузер → sql.js (или jeep-sqlite) | на устройстве открывается файл БД; в браузере данные не теряются |
| 4.4 | P2 | Резервное копирование | `CapacitorSQLite.exportToJson` или копирование файла БД в файловую систему/облако | есть кнопка «бэкап» или автобэкап |
| 4.5 | P1 | Версионирование схемы нативного SQLite | Синхронизировать «эталон» из Фазы 2 с версионированием плагина (`upgrade`/`setVersion`) | схема на устройстве совпадает с эталоном |

> ⚠️ Любое изменение схемы (Фаза 2) должно быть сделано **до** перевода Android на нативный
> SQLite, иначе придётся мигрировать данные уже на устройствах. Поэтому Фаза 2 идёт раньше Фазы 4.

- **Документация**: после Фазы 2 и 3 обновить `docs/DATA-MODEL.md` (схема станет «эталонной»),
  а после Фазы 7 — `docs/API-INTEGRATION.md` (контракт API может уточниться).
- **«Что я не стал делать сразу»**: реальная мультимастерная синхронизация с разрешением
  конфликтов по полям (CRDT/version vectors) — это следующий уровень после стабильного
  last-write-wins; для мастерской на 1–3 устройства LWW достаточно.

## Что делать в первую очередь (быстрый старт по плану)

1. **Фаза 0.1–0.4** (мусор + lint) — 2–3 часа, сразу даст чистую базу.
2. **Фаза 1.1–1.3** (персистентность sql.js) — 1 день, устранит потерю данных.
3. **Фаза 2.1–2.3** (миграции + деньги) — 1–2 дня, развяжет руки для нативного SQLite.
4. Дальше по приоритету: Фаза 3 (синк) → Фаза 4 (Capacitor SQLite) → Фаза 5 (тесты).
