# План развития Ledger Craft (дорожная карта)

> Этот план составлен по результатам ревью кода (см. `docs/ARCHITECTURE.md`,
> `docs/FRONTEND.md`, `docs/API-INTEGRATION.md`, `docs/DATA-MODEL.md`). Он фиксирует **что**, **зачем**
> и **в каком порядке** делать, чтобы проект перестал «терять данные» и начал честно работать
> как offline-first система.
>
> Приоритеты: **P0** — данные теряются/невозможно работать в проде, **P1** — больно и дорого
> поддерживать, **P2** — хочется, но не блокирует.
>
> Оценки объёма — «человеко-дни» для соло-разработчика, который уже знаком с кодом.

## 0. Итоговая дорожная карта (одним взглядом)

| Этап | Что даёт | Объём |
|---|---|---|
| **Фаза 0** — гигиена репозитория | чистая база, lint проходит, меньше шума | ~1 день |
| **Фаза 1** — персистентная локальная БД | данные переживают перезапуск приложения | ~1–2 дня |
| **Фаза 2** — схема и миграции | одна истина в схеме, единые деньги, честные транзакции | ~2–3 дня |
| **Фаза 3** — переписать синхронизацию | связные таблицы синкаются, без костыля «двойной прогон»; бэкенд: SAVEPOINT, идемпотентность, удаления, владелец | ~3–5 дней (FE) + ~2–3 дня (BE) |
| **Фаза 4** — нативный SQLite (Capacitor) | Android: настоящий SQLite на диске | ~1–2 дня |
| **Фаза 5** — тесты | регрессии ловятся автоматически (особенно по синку) | ~2–3 дня |
| **Фаза 6** — UX офлайна | приложение не блокируется на синке, есть индикатор сети | ~1–2 дня |
| **Фаза 7** — конфигурация и безопасность | env, токены, осмысленный вход + гигиена API бэкенда | ~1–2 дня (FE) + ~1 день (BE) |
| **Фаза 8** — рефакторинг UI | OrderDetailsPage 1042 строки → компоненты | ~1–2 дня |
| **Фаза 9** — продукт (аналитика, склад, материалы) | аналитика, маржа/наценка, склад, ручные позиции | ~3–5 дней (FE) + ~2–3 дня (BE) |
| **Фаза 10** — специализации и пресеты (мульти-профиль) | новый юзер получает готовый каталог своей ниши, UI говорит на его языке; мастер может вести две специализации | ~4–6 дней (FE) + ~2–3 дня (BE) |
| **Фаза 11** — среды и выкат (dev-VPS → prod-VPS) | живые прогоны и боевой выкат: предсказуемый порядок «фича → dev → prod», закрытые долги из окружения разработки | ~2–4 дня |
| **Фаза 12** — правки по ревью UI (профили и отладка) | специализация только из доступных, статус/оплата одним органом, отладка — в dev-вкладке | ~1 день (FE) |
| **Фаза 13** — обновление Android-приложения (без Play) | приложение само говорит «доступна версия N» и обновляется по кнопке: APK с сервера, sha256, системный установщик | ~2–3 дня (FE) + ~1–2 дня (BE) |
| **Фаза 14** — обратная связь «Сообщить об ошибке» | мастер отправляет отчёт офлайн, отчёт доезжает до инбокса в репозитории, агент читает его и заводит задачу | ~2–3 дня (FE) + ~1 день (BE) |

> **Две платформы.** Задачи помечены **[FE]** (этот репозиторий), **[BE]** (`LedgerCraftDocker03`,
> Laravel) и **[FE+BE]** (одной стороной не закрыть). Для `[BE]`/`[FE+BE]` критерий «Готово»
> проверяется на сервере либо тестом в бэкенд-репо. Серверные коммиты — отдельно от фронта.

> **Почему такой порядок:** сначала чиним то, что убивает данные (Фаза 1–4), только потом
> наводим красоту и добавляем фичи. Странно улучшать UI, пока каждое закрытие приложения
> стирает всю учётку.

## Решения и открытые вопросы

**D1. Синк — только Laravel (принято 11.09.2026, выполнено в 3.11).** `/api/sync` + `/api/sync-updates`
(`SyncController`) остаются единственным транспортом. Go-сайдкар `sync/` вынесен из `master`
в песочницу `../ledger-craft-go-sync-sandbox` (был экспериментом «ускорение + практика языка»),
а две вещи из него перенесены в Laravel: **SAVEPOINT-изоляция операций** (битая операция
откатывается одна, остальные применяются) и **вырезание `server_id`/`*_server_id`** из payload.
Причина: две реализации одного контракта уже разошлись (у Go устаревший список таблиц), а узкое
место синка — не язык, а отсутствие идемпотентности, курсора на таблицу и лимитов выдачи.
Задачи 3.5, 3.11 (закрыты).

**D2. Материалы = позиции заказа (принято 11.09.2026).** Продуктовый замысел: мастер закупает
товар, делает наценку и продаёт клиенту «от себя», а то, что куплено на стороне, вписывает
вручную. В коде это две существующие сущности: товар со склада → `order_product` (со списанием и
возвратом остатка) и **ручная позиция** → строки материалов заказа (`order_id, name, price,
amount`). В обе позиции добавляется **`buy_price`** (себестоимость) → считается маржа/наценка.
Клиентский справочник `materials` (клиентская миграция 018) удаляется, **новая серверная таблица
`order_material` не нужна** (её семантику уже выполняет серверная `materials`). Задачи 3.4, 9.5, 9.6.

**D3. Web-версия бэкенда — продукт (принято 12.09.2026).** `resources/js` + blade'ы +
`save_order`/`update_order` + `Auth::routes()` не легаси: её сохраняем и не удаляем, поэтому объём
задачи 7.6 ограничен чисткой мёртвого/дублирующего (недостижимый `auth:api`, дубль
`switch_paid_status`, не зароутенный `MaterialController::create`). Публичный отчёт `/order-report`
остаётся и связан с share-ссылкой (задача 9.4).

**D4. Специализация = рабочий профиль, а не «тип аккаунта» (принято 12.09.2026).** Уже сейчас это
сквозная ось: на сервере `User hasMany Specialization` (`specializations.user_id`), на клиенте к
`specialization_id` привязано всё — `categories` → `services`, `product_categories` → `products`,
`equipment_models`, `clients`, `orders`; синк фильтрует выдачу по цепочке владельцев (3.10).
Поэтому «веломастер + аквариумист» под одним аккаунтом **не требует переделки схемы** — нужны
продуктовая оболочка и UX: активная специализация = `useSpecializationsStore.selectedId`,
переключение — смена рабочего контекста, не выход из аккаунта. Переключатель переезжает из
«Другие» в шапку → задача 10.8.

**D5. Пресеты специализаций + адаптация UI (принято 12.09.2026).** Пресет = стартовый каталог
(категории работ → услуги с ценами, категории товаров, модели) + метаданные UI (лексикон терминов,
акцент, видимость вкладок). Правила: **клонируем, а не ссылаемся** (применённый пресет — обычные
записи мастерской с пометкой `template_key`); **идемпотентность** повторного применения (10.4);
**источник пресетов — сервер** + read-only кэш на клиенте и фолбэк на клиентский JSON (10.7);
**архив вместо удаления** специализации (каскадный FK снёс бы каталог — 10.6/10.8); **раскраска
только акцентом** через runtime `setCssVar` (10.2); **схему заказа по нишам не ветвим** —
универсальная модель + максимум одно опциональное поле `equipment_identifier` (10.9).
Первые четыре специализации **v1**: ремонт велосипедов (`bike`), мастер по аквариумам
(`aquarium`), установка и обслуживание кондиционеров (`hvac`), автосервис (`auto`); перечень
расширяется, потому что пресеты — это контент, а не код. Подробные правила — `TODO.md` §Решения,
разделы — `docs/DATA-MODEL.md` («Рабочие профили…») и `docs/FRONTEND.md` §9.
**Не делаем (осознанно):** schema-per-ниша, отдельные формы заказа под специализацию,
CRDT/version-vectors — выигрыш близок к нулю, а офлайн-модель и синк ломаются.

## Фаза 3 — Переписать синхронизацию (P0, самый большой кусок)

**Зачем:** сейчас `sync()` дважды вызывает `_syncLocalToServer()` — это костыль под
двухфазную отправку «родитель → ребёнок», но он не гарантирует порядок. Операции детей
откладываются просто «в очередь», если у родителя ещё нет `server_id`. А `order_product`
и ручные позиции материалов вообще не участвуют в синке — их INSERT улетают с локальным UUID
в `order_id`, а обратно не приходят.

Кроме клиента у Фазы 3 есть вторая половина: `/sync` и `/sync-updates` на сервере не под auth,
не знают владельца записи (`orders.user_id` теряется), не умеют идемпотентность, изолировать
сбойную операцию и сообщать об удалениях. Без этого «офлайн-first» остаётся фикцией, поэтому
задачи 3.4–3.6, 3.8 помечены **[FE+BE]**, а 3.9–3.12 — **[BE]**.

### Задачи

| ID | Приоритет | Задача | Действия | Критерий «Готово» |
|---|---|---|---|---|
| 3.1 `[FE]` | P0 | Убрать двойной вызов `_syncLocalToServer()` | Удалить вторую строку в `sync()` | в `sync()` вызов `_syncLocalToServer()` — один ✅ (сделано) |
| 3.2 `[FE]` | P0 | Топологическая сортировка операций | Перед отправкой строить граф зависимостей из `fkTransformationMap` и `*_server_id`-полей; отправлять родителей раньше детей; если зависимость не готова — откладывать конкретную операцию, а не весь батч; дожимать отложенных внутри одного прогона | ребёнок никогда не отправляется раньше родителя, очередь не оставляет «сирот» за один `sync()` |
| 3.3 `[FE]` | P0 | Статусы операций (не удалять сразу) | В `operations` добавить `status` (`pending`/`sending`/`synced`) и `updated_at`; `dequeue` берёт только `pending`; `markSynced` удаляет только после атомарного успеха | операция не «теряется» при сбое между отправкой и ответом |
| 3.4 `[FE+BE]` | P0 | Подключить связные таблицы | FE: `order_product` и ручные позиции материалов в `repos` + `fkTransformationMap`, `applyServerRecord` (server_id → локальные UUID). BE: `order_product` уже в `$tables` (generic-путь ок); для ручных позиций — существующая серверная `materials` (решение D2, новую таблицу не создаём) | тест: созданный офлайн ордер с работой, товаром и ручной позицией уезжает и приезжает на второе устройство |
| 3.5 `[FE+BE]` | P1 | Идемпотентность | BE: `uuid_id`/уникальный ключ + `updateOrInsert` вместо `insertGetId` (у `order_service` нет PK → `order_id+service_id` или `uuid_id`); сюда же перенос SAVEPOINT-изоляции из Go (3.11). FE: считать операцию доставленной только при явном ответе сервера | повторная отправка того же батча не создаёт дублей (тест на сервере) |
| 3.6 `[FE+BE]` | P1 | Курсор `last_synced_at` на таблицу | FE: `key = 'last_synced_at:<table>'` или колонка `table` в `meta`. BE: колонки `last_sync_id` (анти-эхо) — код уже написан и включится сам | после сбоя в одной таблице другие продолжают с прошлого курсора; устройство не получает свои же записи |
| 3.7 `[FE]` | P1 | Обработка ошибок сети | Эскалация ретраев (backoff), при сетевой ошибке операция остаётся в очереди, UI показывает «нет сети» | нет бесконечного цикла отправки одного батча |
| 3.8 `[FE+BE]` | P1 | Версионирование/конфликты | `updated_at`-сравнение оставить как начальную версию, но задокументировать известные конфликты (last-write-wins); BE: `updated_at` проставляет сервер — клиент обязан его применять | поведение при конфликте описано и покрыто тестом |

## Фаза 13 — Обновление Android-приложения без Play (P0/P1) — 🔧 в работе

**Зачем:** приложение уже живёт на телефонах мастерских, но обновить его сейчас можно только
переустановкой APK руками. Нужен свой канал обновления: сервер знает актуальную версию, приложение
показывает «доступна версия N» и по кнопке обновляется — без Google Play и без Cordova (решение **D6**).

**Физика вопроса (не обойти):** Android разрешает «тихую» установку только для Play (In-App Updates)
или владельцу устройства (Device Owner/MDM). При раздаче APK со своего сервера система **всегда**
показывает диалог подтверждения — значит задача формулируется как «одна кнопка и один тап», а не
«совсем без участия пользователя». Обновление JavaScript внутри WebView политика Play разрешает,
обновление самого APK — нет; поэтому канал раздачи выбран свой (APK), а OTA веб-слоя — отдельный этап.

## Фаза 14 — Обратная связь: «Сообщить об ошибке» (P1/P2) — 🔧 в работе (14.1–14.7 сделаны)
