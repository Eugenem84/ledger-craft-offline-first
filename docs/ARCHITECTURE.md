# Архитектура Ledger Craft

> Offline-first система учёта для мастерских: приём заказов (ордеров), клиенты, каталог
> работ и услуг, склад запчастей, модели техники, аналитика. Приложение обязано работать
> без интернета, а при появлении сети — синхронизироваться с сервером.

## 1. Общая схема слоёв

```
┌─────────────────────── UI (Quasar / Vue 3) ───────────────────────┐
│  Pages (OrdersPage, OrderDetailsPage, StorePage, CatalogPage,     │
│         AnalyticPage, OthersPage)                                  │
│         │  читают/пишут состояние                                  │
│         ▼                                                          │
│  Pinia stores (useOrdersStore, useClientsStore, ...)               │
│         │  вызывают                                                │
│         ▼                                                          │
│  Repositories (*Repo)  ─── операции ──► operationsRepo             │
│         │                                 (очередь INSERT/UPDATE/  │
│         ▼                                     DELETE для сервера)  │
│  Queries (готовые SQL-строки)                                     │
│         │                                                          │
│         ▼                                                          │
│  Adapter БД                                                        │
│   ├─ sqljs-web-adapter.js   (используется сейчас: sql.js в памяти) │
│   └─ sqlite-capacitor-adapter.js (заготовка под нативный SQLite)   │
│         ▼                                                          │
│  Локальная БД (SQLite через sql.js)                                │
└──────────────────────┬─────────────────────────────────────────────┘
                       │  SyncService (services/syncService.js)
                       │    local→server: очередь operations → POST /api/sync
                       │    server→local: GET /api/sync-updates?table=&since=
                       ▼
               Axios (services/api.js, заголовок X-Sync-ID)
                       │
                       ▼
        Laravel API на Beget (https://dev.medovf2h.beget.tech/api)
```

## 2. Ключевая идея: локальный `id` и серверный `server_id`

Каждая запись имеет два идентификатора:

- **`id`** — локальный, `TEXT`, UUID v4. Генерируется на устройстве мгновенно. Именно это
  позволяет создавать записи полностью офлайн (без ожидания сервера).
- **`server_id`** — серверный, `BIGINT/INTEGER`. Присваивается только после того, как
  запись уехала на сервер (на сервере это автоинкремент).

Ссылки на другие записи (внешние ключи) тоже хранятся в паре:
`xxx_id` (локальный UUID родителя) + `xxx_server_id` (серверный id родителя).

**Правило согласованности:**
- внутри устройства всё связано по локальным `id` (UUID);
- на сервер уходят только серверные id (`server_id`);
- если у родителя ещё нет `server_id`, операция, ссылающаяся на него, **не может быть
  отправлена** — она откладывается точечно и дожимается в следующей «волне» того же `sync()`
  (задача 3.2).

Именно эта «связность через server_id» порождает почти все баги синхронизации в истории
проекта (коммиты про «нет server_id у order_service» и т.п.).

## 3. Порядок запуска приложения (boot)

Ключевой boot-файл — `src/boot/db.js` (Quasar запускает его до рендера приложения):

1. `dbAdapter.init()` — создаёт БД sql.js **в памяти**.
2. Создаёт служебную таблицу `migrations` и применяет миграции из
   `src/database/migrations/index.js` (каждая — один раз, по `id`).
3. `await syncService.sync()` — синхронизация **блокирует загрузку UI**
   (пока выполняется сетевой обмен, приложение не рисуется).
4. Остальные boot-файлы: `axios.js` (дефолтный axios Quasar) и `pinia.js`.

## 4. Синхронизация (подробно)

### 4.1. Направление local → server

1. Любое изменение пишется **сразу** в локальную БД и в очередь `operations`
   (`id`, `type`: insert/update/delete, `table`, `payload` JSON, `status`, `created_at`,
   `updated_at`). Статус операции: `pending` (ждёт отправки) → `sending` (улетела, ответа
   ещё нет) → `synced` (сервер подтвердил, идёт «примирение» локальной записи).
2. `_syncLocalToServer()` (в `syncService.js`) сначала возвращает в работу «зависшие»
   in-flight операции (`operationsRepo.recoverInFlight()`: `sending` → `pending`,
   `synced`+insert → `pending`, `synced`+update/delete → удаление), затем работает
   «волнами» — не больше `MAX_SYNC_WAVES = 5` за один `sync()`:
   - выгружает очередь через `operationsRepo.dequeue()` — только `pending` (операции, по
     которым сервер уже ответил в этом прогоне, повторно не берутся);
   - парсит `payload` и готовит внешние ключи (`_prepareForeignKeys`):
     - «сигнальное» поле вида `xxx_server_id` → значение подставляется в `xxx_id`,
       сигнальное поле удаляется из payload;
     - локальный `xxx_id` → ищется `server_id` в таблице-родителе;
   - строит граф зависимостей (`fkTransformationMap` + локальные id родительских операций
     батча) и сортирует операции топологически (`_sortByDependencies`, алгоритм Кана):
     родители уезжают раньше детей; тай-брейк — `TABLE_ORDER`, затем `created_at`;
   - операция с **неготовым** FK откладывается точечно (остальной батч уезжает);
   - помечает батч `sending` (`operationsRepo.markSending`) и отправляет одним
     `POST /api/sync` — «отправлено» фиксируется **до** сетевого вызова.
3. Обработка ответа `{ synced: [...], errors: [...] }` (`_findSyncResult` → `_sendOperations`):
   - insert → `operationsRepo.markSynced` в одной транзакции удаляет операцию и проставляет
     локальной записи `server_id` из ответа;
   - ошибка по операции → `markPending`: операция **остаётся** в очереди и не отправляется
     повторно в этом же прогоне (набор «уже отвеченных» операций);
   - ошибка сети (исключение из `api.send`) → `markPending` для всего батча;
   - 200 OK без результата по операции → помечается как `already_applied` и удаляется из очереди.
4. Волна повторяется, пока есть прогресс (сервер подтвердил хотя бы одну операцию) и остались
   готовые операции: ребёнок, чей родитель получил `server_id` в предыдущей волне, уезжает
   **в том же** `sync()`. Прогон прекращается, когда очередь пуста, готовых операций нет или
   сервер не подтвердил ни одной.
5. Сбой приложения между отправкой и ответом операцию **не теряет**: она осталась в очереди
   (`sending`/`synced`), а следующий `sync()` возвращает её в работу. Повторная отправка до
   появления серверной идемпотентности (задача 3.5) может создать дубль — это осознанный выбор
   в пользу «не потерять данные».

> ✅ Двойной вызов `_syncLocalToServer()` (костыль под двухфазную отправку «родитель → ребёнок»)
> убран в задаче 3.1, детерминированный порядок и «дожим» отложенных операций сделаны в
> задаче 3.2 (граф FK + топосортировка + волны), а статусы очереди и восстановление после
> сбоя — в задаче 3.3. Проверено рантайм-сценариями в Node на настоящем SQLite: заказ офлайн
> (категория/клиент → услуга → заказ → связь «заказ-услуга») уезжает за один `sync()`, очередь
> пуста; битый FK откладывается точечно; сбой «после отправки, до ответа» и недоступная сеть
> не теряют операцию, а возвращают её в работу.

### 4.2. Направление server → local

`_syncServerToLocal()` (в `syncService.js`):

1. Берёт метку `last_synced_at` из таблицы `meta`.
2. Для каждой таблицы из `this.repos`:
   `GET /api/sync-updates?table=<table>&since=<last_synced_at>`.
3. Для каждой полученной записи вызывает `repo.applyServerRecord(record)`:
   - ищет локальную запись по `server_id`;
   - не найдена → вставляет (с новым локальным UUID);
   - найдена → сравнивает `updated_at` и обновляет, если серверная версия новее;
   - серверные FK переводятся обратно в локальные UUID через таблицы-родители.
4. В конце обновляет `last_synced_at = Date.now()` (одна метка на все таблицы).

### 4.3. Что синхронизируется, а что нет

В `syncService.repos` и `fkTransformationMap` **включены**:
`specializations`, `categories`, `product_categories`, `equipment_models`, `clients`,
`services`, `products`, `orders`, `order_service`.

**Не включены** (создаются локально, но синком не обрабатываются): `order_product`,
`order_material`, `materials`, `incoming_products`, `product_stocks`, `buy_product_prices`,
`sales_products_prices`. У последних четырёх есть назначение (приходы / остатки / цены), но
офлайн-слой ещё не подключён — см. `docs/DATA-MODEL.md` и задачи 9.2/9.3.

## 5. UI и состояние

- Страницы напрямую не ходят в БД; они используют Pinia-сторы.
- Сторы делают «оптимистичное» обновление: сначала меняют `items`, потом зовут репозиторий,
  при ошибке откатывают состояние.
- Часть страниц всё же ходит в репозитории напрямую (`OrderDetailsPage.vue`), минуя сторы —
  это исторически сложившийся разнобой.

## 6. Роли файлов (кратко)

| Путь | Роль |
|---|---|
| `src/boot/*` | инициализация при старте (axios, БД + миграции + синк, pinia) |
| `src/services/api.js` | axios-клиент к серверу (единственное место сетевых вызовов) |
| `src/services/syncService.js` | движок синхронизации |
| `src/repositories/*` | работа с локальной БД + постановка операций в очередь |
| `src/repositories/operationsRepo.js` | очередь `operations` (статусы `pending`/`sending`/`synced`, восстановление in-flight операций) |
| `src/repositories/metaRepo.js` | метаданные (в т.ч. `last_synced_at`) |
| `src/database/adapters/*` | абстракция «БД» (sql.js сейчас, Capacitor — заготовка) |
| `src/database/migrations/*` | версии схемы локальной БД |
| `src/database/queries/*` | SQL-запросы для репозиториев |
| `src/stores/*` | Pinia-сторы (состояние UI-сущностей) |
| `src/pages/*` | страницы; `src/pages/dialogs/*` — модальные диалоги |

## 7. Главные архитектурные проблемы

1. **БД не сохраняется на диск** — offline-first фактически не работает после перезапуска
   приложения.
2. **sql.js грузится с CDN** — для старта приложения нужен интернет.
3. **Sync-движок** отправляет операции волнами с топологической сортировкой по FK и
   статусами очереди (задачи 3.1–3.3), но курсор `last_synced_at` — один на все таблицы,
   а не на таблицу (задача 3.6), нет координации одновременных `sync()` из разных вкладок
   (флаг `syncing` живёт только в памяти), а повторная отправка «подозрительной» операции
   до появления серверной идемпотентности может дать дубль (задача 3.5).
4. **Платформенный слой** раздвоен: `sqlite-capacitor-adapter.js` — правильный целевой
   адаптер под Android (Capacitor + нативный SQLite), но он не подключён, а зависимости
   `@capacitor-community/sqlite` в `package.json` нет; папка `src-capacitor` в репозитории
   отсутствует, поэтому продакшен-сборка Android из репозитория не воспроизводится.
5. **Синхронизация связных таблиц** (`order_product`, `order_material`) просто не доработана.

Подробности, карта файлов и известные баги — в `docs/FRONTEND.md` и `docs/DATA-MODEL.md`.
